# Finding F-000: Premature Task Completion on Stream Death

- **ID:** F-000
- **Status:** Diagnosed (Platform Kernel Defect)
- **Component:** Platform Kernel Adapter (`platform/pi/kernel-adapter.ts`)
- **Severity:** Critical (False-Success Sensor Bug)

## Timeline & Evidence

1. **Stream Interruption:** During execution, upstream model streams occasionally terminate prematurely without a standard `finish_reason` ("Stream ended without finish_reason").
2. **Platform Finalization:** When Pi's session event lifecycle fires `agent_end` or finalization, the platform's `kernel-adapter.ts` invokes `finishTask()`.
3. **No-Tool Fallback Defect:** Because `toolExecutionCount === 0` (or tool calls were unvalidated), `finishTask()` executes the "No-tool task" code path. It fabricates a plan with step `response`, observes `"Assistant response produced"`, validates it successfully, and unconditionally transitions the task status to `COMPLETED`.
4. **Tool Rejection Lockout:** Meanwhile, the model continues reasoning and attempting subsequent tool calls. When the model requests a tool, `precheckToolCall()` checks `REFUSED_EXECUTION_STATES.includes(this.task.status)` (which includes `COMPLETED`) and rejects every tool call with:
   \`\`\`text
   Task is COMPLETED; no further tool calls are accepted
   \`\`\`

## Ownership Verdict

**PLATFORM (Repo-Owned)**
- The error message string and the premature terminal transition logic are located in `platform/pi/kernel-adapter.ts` (lines 251 and 829/876).
- Pi core merely reports stream death; the platform orchestrator/kernel adapter incorrectly interprets stream termination as a successful "no-tool task response produced".

## Fix Design (DO NOT IMPLEMENT)

1. **Stream Status Separation:** Distinguish between a clean terminal assistant response and an abrupt stream termination / error.
2. **No-Tool Completion Gate:** A no-tool task must only transition to `COMPLETED` when accompanied by a valid, complete assistant message payload with a normal `finish_reason`.
3. **Error/Recovery Routing:** If a stream ends without a finish reason or throws an incomplete stream error, transition the task to `FAILED` or `RECOVERING` rather than `COMPLETED`, keeping error recovery pathways accessible.

## Gauntlet Blockage Impact

An instrument with a known false-success mode (`COMPLETED` on stream death) cannot reliably certify gauntlet results. This finding must be acknowledged in `reports/REPORT.md`.

## FIX IMPLEMENTED

- **Commit Hashes:** `538d370`, plus subsequent patch for typed terminal signals.
- **Status:** Resolved & Verified
- **Design Decision (Stream Death):** Deliberate fail-closed simplification; recovery machinery is bypassed for stream deaths. Every stream death is terminal `FAILED` (`failureReason: "Stream ended without finish_reason"`). Consequence: `auto/gemini` flakes are terminal per task; gauntlet Rule-5 retry and runner resumability absorb this.
- **Strict Typed Terminal Signal:** `isCleanTerminal()` requires explicit assistant message structure (`role === "assistant"`) with non-empty text content and/or explicit `finish_reason`/`stopReason`. Any untyped result object (including test scaffolding or unrecognized shapes) never completes a task.
- **Tests Added (`platform/pi/stream-termination.test.ts`):**
  1. `stream death never completes task (F-000 regression)`
  2. `clean text-only completion completes successfully`
  3. `tools remain available in RECOVERING; locked in COMPLETED and FAILED`
  4. `untyped result object never completes a task`
